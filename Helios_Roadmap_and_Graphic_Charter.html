01 · PROJECT DEFINITION

What Helios is meant to prove

Helios is not a decorative smart-home dashboard. It is a configurable virtual energy installation. Its simulation engine models photovoltaic generation, household demand, battery storage, conversion limits and grid exchange at a defined timestep. A management layer first runs a transparent baseline, then a forecast-aware policy. The interface makes the resulting state and decisions inspectable.

The first release is software-only. It must be useful without an ESP32, physical solar panel, battery, or live sensor. Future hardware can replace selected simulated inputs, but it must not require rewriting the energy-management rules.

02

PHASE 02 · Weeks 2–3

System model & energy mathematics

Build the numerical heart of Helios before the 3D house. The simulator is the source of truth.

PHASE OUTPUTDeterministic energy engine with unit tests
IDTask & implementation actionsAcceptance condition
02.1 Choose the simulation timestep

Start with a configurable 5- or 15-minute timestep for day-scale simulation. Define timestamps as timezone-aware instants and store all energy internally in Wh/kWh and power in W/kW.

 DONE WHEN

A full day produces the expected number of steps and daylight/timezone boundaries are correct.
02.2 Define canonical units

Use W for instantaneous power, Wh for interval energy, kW/kWh for larger display values, °C for temperature, and percent or 0–1 consistently for SOC. Add explicit conversions at boundaries.

 DONE WHEN

No calculation silently adds power to energy or mixes Wh and kWh.
02.3 Define the energy-balance equation

For each timestep calculate PV energy + grid import + battery discharge = household load + battery charge + grid export + conversion/loss terms. Choose a sign convention and document it.

 DONE WHEN

Energy-balance residual stays within a defined numerical tolerance on every simulated step.
02.4 Define component interfaces

Specify typed inputs/outputs for PV, inverter, battery, appliance, grid, weather, scheduler, and simulation clock. Components must not reach into UI state.

 DONE WHEN

The engine runs in a headless test without rendering React or Three.js.
02.5 Implement simulation clock

Support start, pause, resume, reset, speed multiplier, step-forward, and deterministic replay from a scenario seed.

 DONE WHEN

The same scenario and seed reproduce identical results.
02.6 Implement event-driven state transitions

Define events for appliance start/stop, SOC thresholds, grid outage/return, forecast update, inverter limit, and optimization action.

 DONE WHEN

Every event has timestamp, source, payload, and stable event ID.
02.7 Add numerical guards

Clamp only physically bounded states; reject impossible inputs; prevent negative energy, SOC above capacity, and silent NaN propagation.

 DONE WHEN

Property-based tests cover boundary and extreme conditions.

PHASE 03 · Weeks 3–4

Solar generation & environment model

Estimate PV production from solar position, weather, panel properties, and system losses.

PHASE OUTPUTPV model, weather adapter, production traces
IDTask & implementation actionsAcceptance condition
03.1 Define installation geometry

Configure latitude/longitude, panel tilt, azimuth, installed DC capacity, panel count, and optional shading profile. Do not assume a tracking array unless explicitly enabled.

 DONE WHEN

A scenario file fully describes panel geometry and rated capacity.
03.2 Calculate solar position

Integrate a solar-position library or validated algorithm for elevation and azimuth. Handle local timezone, daylight-saving changes where relevant, and polar/night edge cases.

 DONE WHEN

Known test dates/locations produce plausible sunrise, solar noon, and sunset values.
03.3 Build weather data adapter

Use Open-Meteo as an optional external input for irradiance/cloud/temperature forecasts, with a cached sample and deterministic synthetic-weather fallback.

 DONE WHEN

The simulator still runs offline; provider failures are visible and do not corrupt state.
03.4 Model plane-of-array irradiance

Convert available irradiance inputs to panel-plane irradiance using a documented simplified transposition approach; explicitly label approximations.

 DONE WHEN

The model responds plausibly to sun angle, cloud cover, and panel orientation.
03.5 Model panel temperature and derating

Estimate cell temperature from ambient temperature/irradiance using a simplified documented model; apply a configurable temperature coefficient and system derate.

 DONE WHEN

Higher panel temperature reduces output according to the configured coefficient.
03.6 Calculate PV power and interval energy

Compute DC output from irradiance and rated capacity, apply temperature/soiling/shading/availability losses, then inverter efficiency and AC limit.

 DONE WHEN

Output is zero at night, bounded by inverter capacity, and never exceeds physical limits.
03.7 Model shading and soiling scenarios

Add configurable shading windows and soiling loss factors; make them scenario controls, not hidden random penalties.

 DONE WHEN

A shading/soiling experiment produces an explainable, repeatable production reduction.
03.8 Add optional solar tracking model

If tracking is in MVP, model fixed-tilt vs tracker orientation, tracking limits, stow conditions, actuator energy overhead, and net gain. Otherwise reserve it for extension.

 DONE WHEN

Tracker is only beneficial when additional harvested energy exceeds its own energy cost and constraints.
03.9 Validate PV traces

Compare curve shape against expected clear-sky/daylight behavior and documented sample traces; record assumptions and error sources.

 DONE WHEN

A validation notebook/report includes at least clear, cloudy, hot, and shaded cases.

PHASE 04 · Weeks 4–5

Battery, inverter, grid & storage

Represent storage constraints and conversion losses without pretending to simulate electrochemistry in detail.

PHASE OUTPUTBattery and power-conversion models
IDTask & implementation actionsAcceptance condition
04.1 Define battery parameters

Configure nominal capacity, usable capacity, initial SOC, minimum/maximum SOC, max charge/discharge power, round-trip efficiency, and optional degradation coefficient.

 DONE WHEN

Invalid combinations are rejected and the active battery specification is visible.
04.2 Implement SOC update

Calculate charge/discharge energy per timestep with efficiency and power limits. Enforce SOC bounds and preserve energy accounting.

 DONE WHEN

Hand-calculated cases match implementation within tolerance.
04.3 Prevent simultaneous charge/discharge

Define dispatch precedence and prohibit physically inconsistent simultaneous battery charging and discharging unless a documented topology explicitly permits it.

 DONE WHEN

Invariant tests prove the battery cannot charge and discharge in the same interval.
04.4 Model inverter constraints

Represent DC/AC conversion efficiency, inverter rated power, clipping, standby consumption, and optional export limit.

 DONE WHEN

PV clipping and conversion losses appear in energy accounting.
04.5 Model grid connection

Support grid import/export limits, tariffs, optional export compensation, and outage windows. Keep grid-connected and islanded modes explicit.

 DONE WHEN

An outage removes grid support; restoration is logged and balance remains valid.
04.6 Add battery aging as an extension-ready model

Track equivalent throughput/cycle proxy and configurable capacity fade. Avoid claiming accurate remaining useful life without calibration data.

 DONE WHEN

Aging is clearly marked as an approximation and does not alter baseline runs unless enabled.
04.7 Build storage validation suite

Test empty/full battery, minimum SOC, max power, efficiency loss, outage, and long-duration cycling.

 DONE WHEN

No scenario violates SOC or power constraints; losses are accounted for.

PHASE 06 · Weeks 6–8

Energy management & optimization

Compare a transparent baseline with a forecast-aware policy. Never call a fixed threshold rule 'AI'.

PHASE OUTPUTBaseline controller, optimizer, decision explanations
IDTask & implementation actionsAcceptance condition
06.1 Specify dispatch policy

Define order of use for PV, household load, battery charge/discharge, grid import, and export. Specify reserve SOC and export behavior.

 DONE WHEN

Policy can be described in a state/decision table and is deterministic.
06.2 Implement rule-based baseline

Create a conventional threshold controller using SOC reserve, PV surplus, load demand, and grid state. This is the benchmark strategy.

 DONE WHEN

Baseline runs end-to-end and is reproducible.
06.3 Define appliance scheduling objective

Formalize objective terms such as grid cost, unmet critical load, battery wear proxy, curtailed PV, and schedule inconvenience. Set hard constraints separately from weighted preferences.

 DONE WHEN

Objective function, units, weights, and constraints are documented.
06.4 Implement forecast-aware scheduler

Use forecast PV and expected household demand over a configurable horizon to schedule flexible loads into suitable windows while respecting deadlines and device constraints.

 DONE WHEN

Scheduler emits a feasible plan and explains each deferred/advanced load.
06.5 Add battery reserve management

Maintain configurable reserve for evening demand/outages; avoid discharging below minimum SOC and avoid charging beyond limits.

 DONE WHEN

Reserve behavior is testable under sunny, cloudy, and outage scenarios.
06.6 Add load shedding policy

When supply is insufficient, shed or defer discretionary loads first, then flexible loads; preserve critical loads and expose any unmet demand.

 DONE WHEN

The order is deterministic, visible, and never silently drops critical demand.
06.7 Add surplus-energy policy

Choose among battery charging, flexible-load activation, export, and curtailment according to configuration and tariff assumptions.

 DONE WHEN

Surplus is fully accounted for and the chosen action has a reason code.
06.8 Add decision explanation engine

For every action store trigger, forecast values, constraints, alternatives considered, selected action, and expected effect. Use deterministic templates first.

 DONE WHEN

A user can inspect why an appliance was postponed or a battery reserve was protected.
06.9 Add strategy comparison runner

Run baseline and optimizer on identical scenario seeds, weather, and initial conditions; compare results with paired metrics.

 DONE WHEN

Comparison cannot accidentally use different weather or load traces.
06.10 Add optimization fallback

If forecasts are missing, stale, or invalid, revert to the documented baseline policy and mark the run as fallback mode.

 DONE WHEN

Fallback is automatic, logged, and clearly shown in the UI.

PHASE 07 · Weeks 8–9

Forecasting, anomaly detection & ML

Introduce ML only after the deterministic simulator and baseline produce trustworthy data.

PHASE OUTPUTForecast experiments, anomaly detector, model card
IDTask & implementation actionsAcceptance condition
07.1 Define prediction targets

Separate PV generation forecast, household load forecast, and optional battery SOC trajectory. Define horizon and interval; avoid mixing forecast with ground truth.

 DONE WHEN

Each target has units, horizon, baseline, and evaluation metric.
07.2 Generate or source training data

Create reproducible synthetic scenarios from the simulator and optionally enrich with permitted weather/history data. Tag synthetic data and avoid presenting it as field measurements.

 DONE WHEN

Dataset manifest includes source, generator version, scenario parameters, and split.
07.3 Build naïve forecasting baselines

Implement persistence, time-of-day average, and simple weather-driven baseline before trying ML.

 DONE WHEN

ML is only retained if it improves over a relevant baseline.
07.4 Train PV/load forecasting model

Start with scikit-learn models such as Random Forest or Gradient Boosting; compare with linear baselines. Use time-aware splits, not random row shuffling.

 DONE WHEN

Saved model, preprocessing, feature schema, seed, and evaluation report are versioned.
07.5 Evaluate forecast quality

Report MAE/RMSE and MAPE only where denominator behavior is sensible; include horizon-specific errors and confidence/uncertainty if available.

 DONE WHEN

Forecast report includes sample counts, units, test period, and baseline comparison.
07.6 Implement anomaly detection

Detect unexpected PV underproduction relative to irradiance/temperature expectation, unusual load spikes, and battery/SOC inconsistencies. Start with residual thresholds or Isolation Forest.

 DONE WHEN

Each anomaly has severity, evidence window, expected range, and false-positive caveat.
07.7 Add model monitoring hooks

Track input ranges, missing values, forecast residuals, model version, and fallback frequency. Do not silently retrain on the test set.

 DONE WHEN

A model-health panel exposes drift indicators and stale-model status.
07.8 Write model cards

Document intended use, training data, synthetic-data proportion, metrics, known limitations, and when not to trust the model.

 DONE WHEN

Every ML model has a concise model card linked from the interface/report.

05

Graphic charter · visual identity system

The visual direction is an architectural field atlas: part energy instrumentation, part material study, part domestic cutaway drawing. It should feel designed by a small product studio—not like a generic AI dashboard or a stock green-energy template.

HELIOS · VISUAL IDENTITY 01

“Energy, made legible.”

Quiet mineral surfaces, dark structural ink, oxidized copper for captured solar energy, sage for storage, and a restrained lichen accent for active flows. The visual language borrows from architectural section drawings, field instruments, and printed technical atlases.

02 · Typography

A house in balance.

Literata — editorial headlines, chapter titles, large metrics when emphasis is needed. Use a restrained weight and avoid oversized display text in everyday UI.

Generation · 2.4 kW

DM Sans — navigation, controls, body copy, labels and explanatory text. Prioritize legibility and compact rhythm.

PV-02 / 14:35 / 0840 WH

DM Mono — timestamps, IDs, units, sensor values, model versions and small technical annotations only.

03 · Graphic motif

The signature motif is the sun path / circuit trace: a measured arc crossing a rectilinear house plan, punctuated by small node marks. It can appear as a section divider, loading mark, chart annotation, or cover graphic.

04 · Icon and illustration style

  • Use thin, consistent 1.5–2 px strokes and simple geometric silhouettes.
  • Prefer custom line icons for PV, battery, grid, inverter, appliance and weather.
  • 3D assets use a coherent low-poly architectural style, matte materials and restrained edge detail.
  • Use diagram labels and leader lines rather than decorative floating labels.
  • Avoid gradients, glowing neon outlines, glassmorphism, generic AI sparkles and random green leaves.

05 · Layout and composition

  • Use a 12-column desktop grid, generous outer margins, and consistent 8 px spacing increments.
  • Favor editorial sections, aligned data tables, thin rules and one strong visual per screen.
  • Use cards only when they group a real object or action; not every metric needs a card.
  • Keep chart axes, units and time ranges explicit. Do not remove context to make charts look cleaner.
  • On mobile, prioritize current system state and appliance controls; collapse the 3D scene to a compact view or 2D map.

06 · Data color semantics

  • Oxide: solar generation and PV-derived energy.
  • Sage: battery storage, reserve and healthy component state.
  • Slate blue: grid exchange and environmental context.
  • Lichen: active energy route or selected/interactive state; use sparingly.
  • Signal clay: warning, anomaly or fault. Pair every color with text/icon/pattern; never rely on color alone.
06

Interface and visualization rules

Apply the charter consistently across the 3D twin, dashboard, charts, diagrams, reports and presentation slides.

01 / SURFACESMaterial, not glass

Use limestone/chalk surfaces, basalt structural areas, thin borders and subtle depth. No glossy gradient panels.

02 / ENERGY FLOWSShow direction and magnitude

Use a line, arrow or restrained pulse whose width/speed is mapped to power. Include numeric value on selection.

03 / 3D HOUSEArchitectural cutaway

Consistent camera angle, readable rooms, simple roof geometry and stable object placement. Avoid toy-like clutter.

04 / CHARTSExplain the axis

Label units, interval and source. Use direct labels where possible; avoid unnecessary legends and 3D charts.

05 / STATUSColor plus language

Every status uses a label and icon/shape. Warnings are not conveyed by color alone.

06 / MOTIONMotion has meaning

Animate only actual simulated flows, state transitions or selection. Respect reduced-motion preferences.

07

Evaluation framework & decision gates

These are proposed measurements and gates, not results already achieved. Establish target thresholds after the first working baseline and record them before final testing.

PHYSICS / INVARIANTEnergy balance residual

Per-step supply minus demand and losses; report absolute and relative residual.

ENERGY MANAGEMENTCritical-load uptime

Share of required critical-load intervals served without interruption.

RENEWABLE USEPV self-consumption

PV energy consumed locally divided by total PV energy generated.

ECONOMICSGrid import cost

Imported energy multiplied by the configured time-varying tariff.

STORAGEBattery throughput proxy

Charge/discharge throughput or equivalent-cycle estimate; not a certified aging prediction.

FORECASTINGMAE / RMSE by horizon

Forecast error compared with persistence and time-of-day baselines.

CURTAILMENTUnused PV energy

Available PV that cannot be used, stored or exported under configured limits.

FLEXIBILITYSchedule disruption

Deferred tasks, delay duration and deadline misses for flexible appliances.

SOFTWAREReplay & runtime

Deterministic run match, simulation throughput, load time and 3D frame rate.

PHYSICS GATE

Do not build optimization on top of an energy engine that fails unit tests or energy-balance invariants.

DATA GATE

Do not train ML on synthetic traces and present the result as validated real-world performance. Keep synthetic and external observations separate.

OPTIMIZER GATE

Do not claim improvement unless the baseline and optimizer use identical scenarios, forecasts, initial states and random seeds.

3D GATE

Do not add detailed models before the semantic object map and state binding work. The scene is a client of the simulation.

HARDWARE GATE

Physical ESP32/sensor integration is a later milestone. Add it through an adapter and validate units, timestamps and missing-data behavior first.

CLAIM GATE

Describe Helios as a simulation-based digital twin until it is connected to a real installation with validated telemetry.

The Helios standard

Build a coherent energy model first. Make every decision inspectable. Let the 3D house show the same state the equations calculate. Compare strategies fairly, publish the limitations, and leave a clean path from virtual sensors to physical hardware.
