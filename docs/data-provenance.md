# Data provenance and simulation limits

| Field | Value |
| --- | --- |
| Version | 0.1.0 |
| Date | 2026-11-15 |
| Phase | 00 (task 00.5) |
| Owner | Author (sole developer) |

This document defines what every number in Helios is, where it comes from, and how the interface and the report must label it. The rule is absolute: **a number without a provenance class and a unit is a bug.**

---

## 1 · Why this exists

With no hardware, everything Helios shows is produced by a model. A simulation that presents modelled values as measurements is not a weaker project — it is a dishonest one, and a jury will find the gap. Provenance is therefore part of the engineering, not decoration:

- It prevents the most common overclaim ("our system produced X kWh").
- It makes the comparison between strategies meaningful, because both sides are labelled the same way.
- It tells the reader exactly which conclusions the project can and cannot support.

---

## 2 · Provenance classes

| Code | Class | Definition | Present in v1 |
| --- | --- | --- | --- |
| **M** | Measured | Read from a physical sensor on a real installation | No — requires hardware |
| **X** | External-modelled | Produced by a third-party model or reanalysis (Open-Meteo, ERA5, PVGIS) | Yes |
| **F** | Forecast | Predicted for a future instant from inputs available at issue time | Yes |
| **E** | Estimated | Inferred parameter the twin believes but cannot observe directly (e.g. soiling state) | Yes |
| **D** | Derived | Computed deterministically from other labelled values (energy, cost, ratios) | Yes |
| **S** | Synthetic | Generated by the Helios world model as ground truth (loads, faults, hidden state) | Yes |

Two further rules:

- A derived value inherits the **weakest** class among its inputs. Cost computed from simulated energy and a verified tariff is **D**; the same cost computed from a forecast is **D(F)** and displayed with the forecast badge as well.
- Aggregates (daily totals, percentages) are labelled with the interval count they summarise. A daily total is not more certain than its intervals.

---

## 3 · Interface labelling rules

1. Every numeric widget shows its value, unit and a provenance badge (`M`, `X`, `F`, `E`, `D`, `S`).
2. The badge is explained on hover/focus in plain language, e.g. "Synthetic — generated by the household model, not measured".
3. Forecast values always show issue time and horizon ("issued 06:00, +18 h").
4. Colour is never the only carrier: badge, text and icon must survive grayscale.
5. A cycle, average or total displays the number of intervals and the range it covers.
6. A metric that cannot be computed honestly is **disabled with a reason**, not estimated silently. Example: grid import cost when `tariff.verified` is false.
7. Exported CSV/JSON files include the class, source and run manifest columns; printable views carry the same badges as the screen.
8. Charts label the series class in the axis or legend area, and every figure caption in the report states the class of the plotted data.

## 4 · Metric register

This is the contract for every number the interface may display. Implementation in phase 09 must not introduce a metric that is absent here without updating this register.

| Metric | Unit | Class | Source / formula | Notes |
| --- | --- | --- | --- | --- |
| Global horizontal irradiance | W/m² | X or S | Open-Meteo (forecast/archive) or synthetic generator | Provenance of the weather source is recorded per run |
| Plane-of-array irradiance | W/m² | D | Documented transposition from GHI/DNI/DHI and panel geometry | Approximation, labelled as such (FR-PV-03) |
| Ambient temperature | °C | X or S | Weather source | — |
| Cell temperature | °C | D | Ambient temperature, POA irradiance, NOCT-type model | Simplified thermal model |
| PV DC power | W | D | POA × capacity × temperature factor × (1 − losses) | Loss terms individually attributable |
| PV AC power | W | D | `min(DC × η_inv, P_rated_AC)` | Clipping visible in the loss breakdown |
| Inverter losses | Wh | D | DC energy − AC energy + standby | Standby is a configured constant |
| Household load | W | S | Appliance model, seeded profiles | Sum of appliance contributions (FR-LOD-04) |
| Appliance interval energy | Wh | S | Rated power × run fraction × interval | Per appliance and per room |
| Battery power | W | D | Dispatch decision applied to the battery model | Positive = discharge convention documented in 02.3 |
| Battery SOC | fraction / % | D | Previous SOC + (charge − discharge) with efficiency | Display shows both fraction and percent |
| Grid import / export | W | D | Residual of the balance after local dispatch | Limits enforced |
| PV forecast | Wh per interval | F | Weather forecast × PV model | Issue time and horizon required |
| Load forecast | Wh per interval | F | Load model / learned model | Distinct from synthetic ground truth |
| Energy balance residual | Wh | D | Sum of supply − demand − losses | Diagnostic, tolerance 1 × 10⁻⁶ kWh |
| Unmet critical demand | Wh | D | Required critical energy − served critical energy | Must be surfaced, never dropped silently |
| Curtailed PV | Wh | D | Available PV that cannot be used, stored or exported | Reason code attached |
| Self-consumption ratio | % | D | Local PV use ÷ total PV generation | Both terms labelled |
| Grid import cost | TND | D | Imported energy × verified tariff band | **Disabled** while `tariff.verified` is false |
| CO₂ avoided | kg | D | Avoided grid import × cited emission factor | Source and year required |
| Critical-load uptime | % | D | Served critical intervals ÷ required intervals | Denominator stated |
| Anomaly score | unitless | E | Residual or Isolation Forest output | Never presented as probability |
| Battery throughput | kWh | D | Σ charge + Σ discharge (proxy for wear) | Explicitly not a remaining-useful-life estimate |
| Tracking net gain | % | D | Additional harvest − actuator energy, ÷ fixed-panel harvest | Only when tracking is enabled |

## 5 · Reference sources and verification status

| Source | Used for | Status |
| --- | --- | --- |
| Open-Meteo forecast API | Forward irradiance, cloud cover, temperature | Key-free; used via an adapter with cache |
| Open-Meteo ERA5 archive | Historical weather for repeatable experiments | Key-free; reanalysis, **not** measurement |
| PVGIS (SARAH2 database) | Independent check of simulated daily yield (FR-PV-07) | Model-to-model consistency check |
| NOAA solar calculator or an ephemeris | Independent check of solar position (FR-PV-02) | Reference values recorded in the test fixtures |
| STEG residential tariff | Import cost | **Unverified** — prices are `null`; economics disabled |
| National grid emission factor | CO₂ avoided | Not yet selected; must be dated and cited before use |

## 6 · Implementation contract

- Every time series is created with a declared provenance class; widgets inherit it. Per-number tagging is not required, per-series declaration is.
- The engine emits plain numbers plus a series descriptor (unit, class, source, issue time, horizon); the interface renders the descriptor, never invents one.
- Unit conversion happens only in the display layer (DEC-004).
- A missing source must fail visibly: no default weather, no implicit tariff, no silent zero.

---

## 7 · Limits of this project — state them in the report

1. There are **no measured values** in v1. Every "production" or "consumption" figure is synthetic.
2. Agreement with PVGIS is a **consistency check between two models**, not empirical validation. It catches unit errors, geometry mistakes and implausible loss factors; it does not prove real-world accuracy.
3. ERA5 is a reanalysis product; it is not a sensor record of the site.
4. Household behaviour is a design assumption; real occupancy patterns differ.
5. Battery aging and anomaly models are approximations, explicitly not certification-grade.
6. The comparative claim (scheduler vs baseline) is valid **within the simulation**, under the stated scenarios, seeds and assumptions — not as a field result.
7. Only physical instrumentation could supply class **M** values; that is the first task of any future hardware phase.
